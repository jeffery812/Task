Task {@concurrent in}

关键不是“开了一个 Task”，
而是“这段代码跑在哪条线上”。

Task 用来从当前上下文开启一段新的异步工作；Task { @concurrent in … } 是 Swift 6.2 的写法，明确告诉编译器：这段工作不要在当前 actor 上跑，放到后台去。

Task { @concurrent in
    try await work()
}  // 在 MainActor 上下文中创建
MainActor · 主线程
Global concurrent executor · 后台
work()

继承调用处的 MainActor：闭包体在主线程执行。同步重活会卡 UI。

01

结构化 vs 非结构化“非结构化”指的是：这个 Task 没有父任务，生命周期不受创建它的那段代码的作用域约束。

结构化

async let · withTaskGroup · withThrowingTaskGroup
func loadPage() async
async let header
async let widgets
父任务取消 → 子任务自动取消
  • ✓ 是父任务的子任务，不会比作用域活得更久
  • ✓ 父任务取消，自动传给所有子任务
  • ✓ 子任务的错误自动传给父任务
  • ✕ 只能在 async 上下文里创建，外部拿不到、也不能单独取消

非结构化

Task { } · Task.detached { }
func load()
currentTask = Task { … }
load() 已经返回，Task 还在跑
外层取消 ✕ 不会传进来
  • ✓ 可以从同步代码创建（按钮回调）
  • ✓ 拿着句柄，可以从外部随时 cancel()
  • ✕ 生命周期独立，取消不会自动传入
  • ✕ 句柄要自己保存、自己清空；错误要 await task.value 才拿到

结构化写法

func loadPage() async throws -> Page {
    async let header = fetchHeader()    // 子任务
    async let widgets = fetchWidgets()  // 子任务
    return try await Page(header: header, widgets: widgets)
}   // ← 返回前，两个子任务一定已经结束

名字借自“结构化编程”：代码的缩进结构就是任务的层级结构，没有东西能从作用域里溜出去。没被 await 的子任务会在离开作用域时被取消并等待结束。

非结构化写法

func load() {
    currentTask = Task {          // 没有父任务
        try await fetch()
    }
}   // ← load() 已经返回，Task 还在跑

Task { } 仍继承 actor 隔离、优先级和 task-local 值，这些不需要父子关系，它只是不是子任务。Task.detached 连这些都不继承。

结构化（async let、task group）非结构化（Task {}、Task.detached）
父子关系是父任务的子任务没有父任务
生命周期不超出作用域独立，可以比创建者活得更久
取消自动从父任务传给子任务不传，要手动 cancel() 或转发
错误自动传给父任务存在句柄里，await task.value 时才抛出
从同步代码创建不能可以，这是它最主要的用途
从外部取消不能单独取消某个子任务可以，拿着句柄随时 cancel()
默认
用结构化

已经在 async 函数里、要并发做几件事再汇总时，用 async let 或 task group，取消和错误都自动处理。

只有两种情况
用非结构化

要从同步代码启动异步工作；或任务需要比当前作用域活得更久、需要从外部取消。

SwiftUI
优先用 .task { }

由 SwiftUI 创建并绑定 View 生命周期，消失时自动取消，不用自己管理句柄。

本项目为什么用非结构化：① 按钮回调是同步的，startLoad() 只能写 Task { try await load(model) }；② “只保留最新请求”要求新的 load() 能取消旧请求，需要能保存下来的句柄 currentTask，结构化子任务做不到。代价就是后面几节讲的：自己保存和清空句柄、用 withTaskCancellationHandler 转发取消、用 [weak self]。

Task { } · 非结构化任务从同步代码（比如按钮回调）进入 async 世界最常用的入口。

从创建处继承什么

  • 继承actor 隔离：在 MainActor 里创建，闭包体就在主线程执行

  • 继承task-local 值
  • 不继承取消：外层被取消，它不会跟着取消，生命周期独立

    try await something()
}

句柄 Task<Success, Failure>

API作用

03

Task { @concurrent in } · 明确放到后台只改变“在哪执行”，其他照常继承。

特性

  • 闭包是 nonisolated 的，运行在全局并发执行器（后台线程池），不继承调用处的 actor
  • 优先级、task-local 值仍然继承，这是它和 Task.detached 的区别
  • 跨隔离域：捕获的值必须是 Sendable（本项目 fetch 是 @Sendable 闭包，self 用 weak 捕获）
  • 访问 MainActor 上的东西（self.append、self.state）必须 await，跳回主线程

本项目 · Serial / Async Latest

let task = Task { @concurrent [weak self, fetch] in
    let onMain = isOnMainThread()      // false
    await self?.append("running, main thread: \(onMain)")
    return try await fetch()
}

日志里的 main thread: false 就来自这里。

为什么需要 @concurrent

SWIFT_APPROACHABLE_CONCURRENCY = YES
nonisolated async 默认跟着调用者走

这类函数默认是 nonisolated(nonsending)，主线程调用它，它就在主线程跑。

SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor
没标注的代码都在主线程

app target 默认隔离为 MainActor，ViewModel、View 都在主线程上。

所以
离开主线程要写出来

在函数上加 @concurrent（如 fetch()），或在 Task 闭包上加 @concurrent。

几种写法对比

写法actor 隔离优先级 / task-local取消适用场景
Task { }继承继承独立从同步代码进入 async 世界，并留在当前 actor 上
Task { @MainActor in }明确 MainActor继承独立从后台回到主线程更新 UI
Task { @concurrent in }不继承，后台执行继承独立把耗时工作移出当前 actor
Task.detached { }不继承都不继承独立极少需要，确实要完全脱离上下文时才用
async let / withTaskGroup结构化继承随父任务取消并发执行几件事，然后等它们都完成
SwiftUI .task { }MainActor继承View 消失时自动取消和 View 生命周期绑定的加载
测试里的 uncancellableSleep 用了 Task.detached：让 sleep 不受测试 Task 的取消影响，也不占用 MainActor，用来模拟“取消后还要继续跑一会儿”的工作。
05

取消是协作式的task.cancel() 只是设置一个标记，不会强行停止代码。

task.cancel()
设置取消标记
任务继续运行，直到碰到支持取消的点
Task.sleep 抛 CancellationError
URLSession 抛 URLError(.cancelled)
CPU 密集代码自己检查：
try Task.checkCancellation()
Task.isCancelled

非结构化 Task 要手动转发取消

try await withTaskCancellationHandler {
    try await task.value
} onCancel: {
    task.cancel()   // 调用方被取消时，转发给内部 task
}

onCancel 在哪执行？

在发起取消的那个线程上立即同步执行，不需要等 load() 恢复。Task.cancel() 是线程安全的，所以从任何线程调用都没问题。

06

启动时机与等待结果Task 什么时候开始跑？等结果一定要 withTaskCancellationHandler 吗？

会立即执行吗？

  • 是创建时就提交到全局并发执行器，不需要有人 await task.value 才开始
  • 否不是同步执行：Task { } 提交后马上返回句柄，load() 接着往下跑，两边并行
  • 丢掉句柄不会取消任务，只是再也无法取消它、拿不到它的结果
  • 想在当前线程上同步跑到第一个挂起点，用 Swift 6.2 的 Task.immediate { }，这和 @concurrent 的目的相反

日志顺序：为什么 running 总在 started 之后

// 主线程：load()
append("#n started")
let task = Task { @concurrent … }  // 后台立即开始
currentTask = task
try await task.value          // ← 主线程在这里才空出来

// 后台：闭包
isOnMainThread()              // 马上执行
await self?.append("#n running") // 等主线程空出来

等结果：try await task.value 就够了

withTaskCancellationHandler 只解决一件事：把调用方的取消转发给非结构化 task，因为 task.value 本身不转发。

调用方被取消时加了 handler不加
内部 taskonCancel 立即 task.cancel()，fetch() 在 sleep / URLSession 处抛错完全不知道，继续 sleep 2 秒、发请求、解析
load()很快恢复，抛 CancellationError，状态回到 .idle等 fetch() 全部完成才恢复，照常写 .loaded 并返回值
结果白做的工作被及时停掉浪费网络和 CPU，已取消的调用方还会更新状态

两条取消路径，只有一条需要 handler

  • 被更新的 load() 替换：新调用手里有句柄，直接 currentTask?.cancel()。不需要
  • 调用方自己被取消：取消只到达外层任务，要靠 onCancel 传进去。需要

当前 App 里 startLoad() 的 Task 没人取消，第二条路径暂时不会触发；测试 cancellingCallerCancelsAsyncLatestRequest 依赖它。改成 .task { } 调用后就会真正起作用。

为什么不直接 try await fetch()？

直接调用是结构化的，调用方的取消会自动传进去，不需要 handler。但这样就没有句柄，更新的 load() 无法取消旧请求。

“只保留最新请求”需要能从外部取消的句柄 → 内部 Task；一旦用了非结构化 Task → 需要 handler 补上取消转发。两者是配套的。

如果调用方在进入 withTaskCancellationHandler 之前就已被取消，onCancel 会在进入时立即执行一次，不会漏掉。
07

常见坑

01

以为 Task { } 在后台跑

在 MainActor 上下文里，它仍然在主线程上。需要后台执行时要用 @concurrent。

02

Task 会强引用捕获的对象

执行完之前，捕获的 self 不会被释放。不需要它延长对象生命周期时，用 [weak self]。

03

忘了保存句柄

不保存就无法取消它，也无法知道“当前请求是哪个”。本项目用 currentTask 保存。

04

完成后句柄不会自动清空

需要自己在合适时机把 currentTask 设为 nil（见 finish(...)）。

05

await 之后状态可能已变

重入问题：恢复后要重新检查，比如 guard !task.isCancelled，再决定是否写 state。

06

能用结构化并发就别用 Task { }

SwiftUI 里和页面生命周期绑定的加载优先用 .task { }，View 消失时会自动取消。

得分 0 / 10 · 已答 0

在一个 @MainActor 的 SwiftUI View 里写 Task { heavySyncWork() }，heavySyncWork() 在哪里执行？

B。Task { } 继承创建处的 actor 隔离。在 MainActor 上下文里创建，闭包体就在主线程执行，同步重活会卡 UI。要放到后台得用 @concurrent。

Task { @concurrent in … } 和 Task.detached { … } 的主要区别是？

C。两者都在全局并发执行器上运行。@concurrent 只改变执行位置，优先级和 task-local 值照常继承；Task.detached 什么都不继承，极少需要。

withTaskCancellationHandler 的 onCancel 闭包在什么时候、在哪里执行？

A。onCancel 在调用 cancel() 的线程上同步执行，不等被取消的代码恢复，所以里面只能做线程安全的事（如 task.cancel()）。如果进入前已被取消，进入时会立即执行一次。

调用 task.cancel() 之后会发生什么？

B。Swift 的取消是协作式的。Task.sleep、URLSession 等会响应取消并抛错；CPU 密集代码需要自己 try Task.checkCancellation() 或检查 Task.isCancelled。

下面哪个不会自动响应任务取消？

D。普通同步循环不知道取消这回事，会一直跑完。A 抛 CancellationError，B 抛 URLError(.cancelled)，C 就是用来检查取消的。本项目 fetch() 在解析前调用了 checkCancellation()。

调用方正在 try await task.value（task 是非结构化 Task），此时调用方自己被取消，会怎样？

C。task.value 不会把取消转发给非结构化任务，也不会提前返回。想让 task 跟着停，要用 withTaskCancellationHandler { try await task.value } onCancel: { task.cancel() }。

下面这段 MainActor 上的代码，最需要注意的问题是什么？

func load() async throws {
    state = .loading
    let value = try await task.value
    state = .loaded(value)
}

A。await 会让出主线程，其他调用可以进来。恢复后可能已有更新的请求，直接写 .loaded 会被过期结果覆盖。本项目用 guard !task.isCancelled 挡住。主线程没有被阻塞（C 错），状态只在 MainActor 上读写，所以不需要锁（D 错）。

开启 Approachable Concurrency 后，从 MainActor 调用一个 nonisolated func parse() async，它在哪执行？

D。此时 nonisolated async 函数默认是 nonisolated(nonsending)，跟着调用者走。要让它离开主线程，需要标 @concurrent，就像本项目的 LandingPageService.fetch()。

SwiftUI 里，和页面生命周期绑定的数据加载，最推荐哪种写法？

B。.task 在 View 出现时启动，消失时自动取消。A 创建的非结构化 Task 不会随页面消失而取消，C 脱离了所有上下文，D 不属于 Swift Concurrency，也没有取消机制。

为什么在 ViewModel 里常写 Task { [weak self] in … }？

C。Task 闭包会持有捕获的值直到执行结束。页面关闭后，如果请求还在跑，强引用会让 ViewModel 多活一段时间并继续更新状态。这不是循环引用（Task 结束后会释放），但通常不是想要的行为。
